TASKPAY — COMPLETE APPLICATION BUILD SPECIFICATION

Build a complete, modern, mobile-first, full-stack web application called TaskPay, with the tagline “Sell. Learn. Earn.”

IMPORTANT: Read the entire specification before building. Build the application as one coherent project. Do not stop after creating a landing page, static mockup or frontend prototype. Do not ask me follow-up questions. Make sensible implementation decisions, preserve working code, and prioritise a functional, secure, well-structured MVP.

1. BUSINESS OVERVIEW

TaskPay is a digital commerce and opportunity platform designed to connect businesses, customers, affiliates, digital creators, event organisers and people seeking legitimate digital work opportunities.

TaskPay combines five core service areas:

1. Online marketplace for physical and digital products.
2. Affiliate marketing, allowing users to promote products and earn commissions on qualifying, verified sales.
3. Paid promotional campaigns connecting businesses with digital promoters.
4. Digital learning, allowing creators to sell courses and users to purchase and access them.
5. Event ticketing, allowing organisers to list events and sell tickets.

The platform must be designed to support expansion beyond Ghana in the future.

The business must generate revenue through vendor memberships, disclosed sales commissions, promotional campaign fees, featured product placements, digital learning commissions and event ticketing fees.

Customers must be able to browse the marketplace without paying an access fee. Never make recruitment of new members the basis of earning commissions.

Build a real full-stack application with:

Do not leave important buttons nonfunctional, create fake payment confirmations, or use hardcoded balances as if they were real money.

14. PAYMENTS AND FINANCIAL LEDGERS

Design the payment system so that Paystack can be configured for supported transactions and mobile money can be explored in a future integration.

Use environment variables for credentials, for example:
PAYSTACK_SECRET_KEY
PAYSTACK_PUBLIC_KEY
PAYSTACK_WEBHOOK_SECRET
APP_BASE_URL

Never expose secret keys to the frontend, commit them to source control or print them in logs.

Use Paystack’s documented payment flow and official server-side verification mechanisms.

A payment must not be marked successful merely because the browser returns to a success page. Verify payment status on the server and validate the amount, currency, reference and transaction identity.

Implement verified webhook handling where supported, including signature validation, duplicate-event protection and idempotent processing.

If credentials are missing, implement a clearly labelled test or configuration state. Do not fabricate successful payments.

19. TESTING AND ACCEPTANCE CRITERIA

Before declaring the build complete, test the following core flows:

1. A customer can register, log in, browse products and view product details.
2. Physical and digital products use separate categories and correct checkout fields.
3. A vendor can apply, be approved by an administrator, create a product and manage orders.
4. An affiliate can obtain a tracking link and see a qualifying conversion only after a verified eligible sale.
5. A business can create a promotional campaign, and an eligible promoter can submit work for review.
6. A course creator can create a course, an administrator can approve it, and an authorised purchaser can access it.
7. An event organiser can create an event, and a customer can purchase and view a ticket after verified payment.
8. Payment status cannot be forged through frontend requests or return URLs.
9. A customer cannot access vendor or administrator dashboards without the appropriate permissions.
10. An administrator can log in through the dedicated admin route and manage users, vendors, categories, products, campaigns, commissions, payouts, settings and reports.
11. The database persists records after reloads and application restarts.
12. Mobile and desktop layouts remain usable.

If a payment integration cannot be tested without real credentials, explain that limitation and provide a test-mode setup. Do not claim the integration is production-ready without verification.
